## Phase 5 — Stronger Models + Fair Comparison (2026-08-16)

### Objective
Compare Logistic Regression (Phase 4's best baseline: VALIDATION F1 0.6599,
PR-AUC 0.7414, ROC-AUC 0.9279) fairly against Random Forest and a gradient
boosting model, without touching TEST or the chronological split.

### What was reused unchanged
`ml/dataset.py`, `ml/split.py`, `ml/train.py`, and -- critically --
`ml/evaluate.py`'s `evaluate_all_baselines()` / `format_results_markdown()`.
The fairness guarantee of this phase rests on all 5 models being scored
through that one unmodified function rather than new metric logic that
could subtly compute things differently.

### What changed
`ml/baseline.py` was refactored (not behaviorally changed) to import its
feature-selection guard from a new shared module, `ml/features.py`, instead
of defining its own private `_select_features()`. `ml/models.py` uses the
same shared guard, so cell_id/date exclusion is enforced identically across
every model in the project, old and new.

### New models
- **RandomForestModel** -- `n_estimators=200, max_depth=20,
  min_samples_leaf=5, class_weight="balanced"`. No hyperparameter search.
- **GradientBoostingModel** -- `sklearn.ensemble.HistGradientBoostingClassifier`
  (`max_iter=200, max_depth=10`), chosen over plain `GradientBoostingClassifier`
  for speed/memory on an 8GB/dual-core machine, and over XGBoost/LightGBM to
  avoid adding a new dependency until proven necessary.

### Class imbalance handling (corrected during implementation)
The original architecture proposal assumed `HistGradientBoostingClassifier`
doesn't expose `class_weight` (true in some older sklearn versions) and
planned a `sample_weight`-based workaround for it. Checking the actual
installed version (sklearn 1.8.0) during implementation showed
`class_weight` IS supported natively -- a unit test asserting the opposite
(`not hasattr(model.model, "class_weight")`) failed immediately and caught
this. Both models now use `class_weight="balanced"` directly, consistently,
with no workaround needed.

### Real results (VALIDATION only, TEST untouched)

| Model | F1 | PR-AUC |
|---|---|---|
| Majority | 0.0000 | — |
| Persistence | 0.4595 | — |
| Logistic Regression | 0.6599 | 0.7414 |
| Random Forest | **0.7082** | 0.8156 |
| Gradient Boosting | 0.6932 | **0.8176** |

Full metrics (precision, recall, ROC-AUC, confusion matrices) in
`docs/phase5-model-comparison.md`, generated by `PYTHONPATH=. python -m ml.compare`.

**Conclusion:** Random Forest is the current candidate -- best F1, and
effectively tied with Gradient Boosting on PR-AUC (0.8156 vs 0.8176, a
0.002 gap not meaningful on its own). Both tree models clear Logistic
Regression by a real margin, confirming the dataset supports more than a
linear model. The F1 gap between Random Forest and Gradient Boosting
(0.7082 vs 0.6932) is measured at the untuned default 0.5 threshold --
Phase 5 did no threshold tuning or calibration, so this gap should not be
read as "Random Forest is the better algorithm," only as the current
snapshot at an arbitrary cutoff.

**No final model selection has occurred.** Random Forest is the leading
candidate for the next phase's threshold/calibration work, not a locked
decision. TEST remains completely untouched -- it will be evaluated
exactly once, after a model is actually chosen.

### Testing
Full suite (`PYTHONPATH=. pytest -q`) -- 140/140 pass. New:
`tests/test_ml_models.py` (Random Forest / gradient boosting fit contract,
cell_id/date exclusion, determinism, class_weight verification) and
`tests/test_phase5_integration.py` (all 5 models through the identical
evaluation path, TEST never referenced -- both a runtime check via
`validate_split_partition` and a source-level check confirming
`evaluate_all_baselines` is only ever called with `val_df`).

### Decisions
- No hyperparameter tuning in this phase -- fixed, hardware-appropriate
  configs only.
- TEST remains untouched. Final model selection and the one-time TEST
  evaluation are deferred until a model is actually chosen for further
  development.
- No MLflow/Airflow/Streamlit/AI layer added -- comparing 5 models via a
  markdown/JSON report (same pattern as Phase 4) was sufficient; MLflow
  earns its complexity once iterating repeatedly across many runs, which
  this phase deliberately isn't doing.

### Next (not started)
Threshold/calibration analysis on VALIDATION for Random Forest (and
optionally Gradient Boosting) -- current F1 numbers use an untuned default
0.5 cutoff, never a deliberate choice. This is also the point where
introducing MLflow becomes justified: multiple threshold/calibration
configurations are worth tracking properly, unlike Phase 4/5's fixed
single-config comparisons. TEST evaluation happens once, only after a
model is locked in following that analysis.
