# EmberRisk Phase 10 — Prediction-Serving API

## Objective

Serve the Phase 6/7 locked model (`HistGradientBoostingClassifier`,
threshold 0.70) via a minimal FastAPI service, so predictions can be
requested on demand rather than only through the Phase 9 batch DAG. This
phase adds a serving layer only — it does not retrain, retune, or
otherwise touch the locked model or any of its reported results.

## Scope: scores supplied features, does not predict "today"

Same limitation as Phase 9, restated here because it applies directly to
how this API should be used and demonstrated: EmberRisk's modeling period
is fixed and historical (`processing.MODELING_START = 2018-01-01`,
`processing.MODELING_END = 2025-12-31`). This API does **not** fetch live
weather/fire data or predict current real-world fire risk. It scores
whatever feature values are supplied in a request:

- **`POST /predict`** scores caller-supplied feature values — real or
  hypothetical, the API has no way to distinguish, and does not claim to.
- **`GET /predict/sample/{cell_id}/{date}`** is a convenience endpoint
  that pulls a genuinely real historical row from the assembled feature
  table and scores it — useful for demos without hand-building a
  15-field JSON payload, but "real" here means "really in the
  2018-2025 historical dataset," not "current."

This is a serving-layer demonstration: proof that the locked model can be
wrapped in a request/response API with proper input validation, not a
live risk-assessment tool.

## Endpoints

| Endpoint | Method | Purpose |
|---|---|---|
| `/health` | GET | Liveness check; confirms model is loaded |
| `/model/info` | GET | Returns locked model metadata (name, threshold, feature columns, training row count) |
| `/predict` | POST | Scores one or more caller-supplied feature rows |
| `/predict/sample/{cell_id}/{date}` | GET | Scores a real historical row by id, for easy demos |

Interactive API docs (auto-generated by FastAPI) are available at `/docs`
when the server is running.

## Design

- **Model loaded once at startup**, via a FastAPI `lifespan` handler
  calling `ml.predict.load_locked_model()` — not reloaded per request.
- **All scoring goes through `ml.predict.score_batch()`**, the exact same
  function used by the Phase 9 Airflow DAG's `score_batch` task. The API
  and the batch pipeline cannot silently diverge in how they score a row,
  because there is only one scoring implementation, not two.
- **Request schema (`api/schemas.py`) is generated from
  `ml.dataset.FEATURE_COLUMNS`**, not hand-typed, so the API's required
  fields can never silently drift out of sync with the model's actual
  feature contract.
- **Verified correctness**: `/predict/sample/65_-183/2018-01-01` was
  manually checked against the same row scored via the Phase 9 standalone
  `ml.predict.score_batch()` call — both returned `0.33880031451963155`
  to full floating-point precision, confirming the API path and the batch
  path are computing identically, not two implementations that happen to
  agree approximately.

## Testing

`tests/test_api.py` (12 tests, using FastAPI's `TestClient` against the
real loaded model artifact, not a mock): health check, model info
correctness, single/multi-row prediction, id echoing, threshold/positive
consistency, and four input-validation failure cases (missing feature
column, empty rows, mismatched id-array length, unknown cell/date).
Combined with the existing suite: **199 tests passing** (187 prior + 12
new).

### Known, non-blocking warnings

- **Starlette `TestClient` deprecation warning** re: `httpx` vs a future
  `httpx2` dependency. Cosmetic, tied to test infrastructure only, not
  runtime behavior — noted for a future dependency bump, not acted on now.
- **`joblib`/NumPy 2.5 array-shape deprecation warning**, surfaced
  repeatedly during the API test run because the model artifact is
  reloaded per test module. Originates from an internal NumPy API used by
  joblib's pickling implementation being deprecated in NumPy 2.5.2 (this
  project's pinned version) — does not affect prediction correctness
  (verified above), but is a signal that a future joblib/numpy upgrade
  should be checked once available.

## How to run locally

```bash
PYTHONPATH=. uvicorn api.main:app --reload
# API: http://localhost:8000
# Interactive docs: http://localhost:8000/docs
```

Example requests:

```bash
curl http://localhost:8000/health

curl http://localhost:8000/model/info

curl "http://localhost:8000/predict/sample/65_-183/2018-01-01"

curl -X POST http://localhost:8000/predict \
  -H "Content-Type: application/json" \
  -d '{"rows": [{"fire_count": 0, "fire_count_3d": 0, "fire_count_7d": 0, "fire_count_14d": 0, "fire_count_30d": 0, "days_since_last_detection": 999, "frp_mean": 0, "frp_max": 0, "frp_mean_7d": 0, "frp_max_7d": 0, "temperature_max": 35, "temperature_min": 20, "relative_humidity": 15, "precipitation": 0, "wind_speed": 25}]}'
```

## What this phase does not do

- Does not retrain, retune, or re-select the locked model/threshold.
- Does not fetch or predict on live/current data.
- Does not deploy the API anywhere (local `uvicorn` only) — containerizing
  and deploying it is noted as possible future work, not built here.

All four endpoints implemented and manually verified against real
