# EmberRisk Phase 13 — Public Deployment

## Objective

Deploy the Phase 10 FastAPI serving layer (and its demo UI) publicly, so
the project has a real, clickable link rather than only running on a
local machine. This phase is about making the existing work reachable,
not adding new modeling or pipeline capability.

## A deliberate exception: the trained model artifact is committed to git

Every prior phase treated `models/` as gitignored — a regenerable build
artifact, not source, produced on demand by
`ml/train_and_save_locked_model.py` from the full local dataset. That
rule still holds for local development and for the Airflow orchestration
path (Phase 9): the artifact there is trained fresh from
`data/processed/cell_day_dataset.parquet`, which itself depends on
~60MB of raw data that has never been and will never be committed to
this repository.

Public deployment is a different situation with a different constraint:
the deployed container has no access to the raw dataset (60MB+, gated
behind a NASA API key, takes real ingestion+processing time to rebuild)
and does not need it — a deployed API only needs to *score* requests
using the already-locked, already-evaluated model, never to retrain one.

For this reason, and only for this reason,
`models/gradient_boosting_locked.joblib` (727KB) and its metadata JSON
are committed to the repository, via an explicit `.gitignore` exception:

```
models/*
!models/gradient_boosting_locked.joblib
!models/gradient_boosting_locked.metadata.json
```

This mirrors a standard distinction in real ML systems between a code
repository and a model registry/release artifact: the *code* that
produces the model stays fully reproducible and version-controlled
(`ml/train_and_save_locked_model.py`, unchanged), while the *specific
trained artifact* used for a specific deployment is treated as a small,
versioned release asset. What has NOT changed:

- The model itself is still the one locked in Phase 6/7 -- same class,
  same hyperparameters, same TRAIN split, same threshold (0.70).
- Nothing about the locked TEST evaluation (`docs/final-results-and-
  limitations.md`) is affected by this decision.
- The full raw dataset, `data/processed/`, and every other regenerable
  artifact remain gitignored, exactly as before.

If the committed artifact ever needs to be refreshed (e.g. after a
deliberate, documented retraining decision under a new protocol), it
would be replaced via the same training script and re-committed
explicitly -- never silently regenerated by CI or a deploy hook.

## Deployment architecture

A standalone `Dockerfile` (project root, separate from
`docker-compose.airflow.yml`) builds a minimal image containing only what
the API needs at runtime: `api/`, `ml/`, `models/`, and
`requirements.txt`. It deliberately excludes `ingestion/`, `processing/`,
`dags/`, `docs/`, and `tests/` -- none of those are needed to serve a
prediction, and including them would only bloat the deployed image.

**Host:** Render, free web service tier, built directly from the
Dockerfile. Chosen for zero-cost entry, native Docker support, and being
a deployment target technical reviewers recognize as a legitimate
hosting platform, not a novelty demo tool.

**What's live:**
- `/` -- the demo UI (scenario picker + build-your-own-scenario builder)
- `/predict`, `/predict/sample/{cell_id}/{date}`, `/model/info`,
  `/health` -- the same API endpoints documented in Phase 10
- `/docs` -- FastAPI's auto-generated interactive API documentation

## What this phase does not do

- Does not retrain, retune, or change the locked model/threshold.
- Does not deploy the Airflow orchestration stack (Phase 9) -- that
  remains a local/self-hosted concern, not part of the public demo.
- Does not add live/current data ingestion to the deployed service -- the
  same fixed-historical-period scope note from Phases 9 and 10 applies
  here unchanged.
